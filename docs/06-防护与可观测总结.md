# 防护与可观测 —— 学习总结

> 结论先行：Agent 死循环是必然事件不是小概率事件，**防护是上线前必备而不是事后补**。

## 死循环的两种形态

| 形态 | 表现 | 检测手段 |
|------|------|---------|
| 调用次数失控 | 反复调用不同工具不停手 | 总次数上限 |
| 参数死循环 | 同一工具同一参数反复调 | 重复签名检测 |

[LoopBreaker](../src/main/java/com/xb/agent/guard/LoopBreaker.java) 两个都做：计数上限 + 最近 3 次签名全相同即熔断。**让 LLM 换参数比重试更有效**——死循环的根源通常是 prompt 里没说清工具怎么用。

## Token 预算的记账粒度

[TokenBudget](../src/main/java/com/xb/agent/guard/TokenBudget.java) 在每次工具 observation 返回后记账，粗估字符数/2。宁可提前停（预算 100k，70k 就警告），也别等账单出来吓一跳——LLM 调用是按 token 计费的黑洞。

## 并发限制必须跨实例

[ConcurrencyLimiter](../src/main/java/com/xb/agent/guard/ConcurrencyLimiter.java) 用 Redis increment 而不是 JVM 信号量：多 Pod 部署时单机信号量限不住全局。**舱壁隔离**（每任务独立虚拟线程池）在本项目由 `newVirtualThreadPerTaskExecutor()` 天然实现。

## 指标里最值钱的一个

[AgentMetrics](../src/main/java/com/xb/agent/observe/AgentMetrics.java) 六个指标里，**幻觉式工具调用次数**（调用不存在的工具）最能反映 prompt 质量——Agent 编造工具名，说明工具清单没注入或描述不清。

HITL 触发率是评估 Agent 能力的反向指标：触发太频繁说明 Agent 能力不足或风险阈值太敏感。

## 链路追踪粒度

[AgentTraceLogger](../src/main/java/com/xb/agent/observe/AgentTraceLogger.java)：任务 = Trace，工具调用 = Span。Span 属性里 observation 截断到 200 字符——**再细存储成本爆炸**，全量走结构化日志带 traceId 检索。日志和 Trace 的分工：日志看细节，Trace 看拓扑。
