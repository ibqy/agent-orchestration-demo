# 工具体系 —— 学习总结

> 结论先行：工具体系的核心是把**发现和执行分离**，横切关注点（权限/熔断/审计）全部收口到一处。

## 注册中心元数据

[ToolDescriptor](../src/main/java/com/xb/agent/tool/ToolDescriptor.java) 的字段是从事故反推的：

| 字段 | 为什么需要 |
|------|-----------|
| permission | 越权调用高危工具的事故 |
| risk (LOW/MEDIUM/HIGH) | 高危工具触发 HITL 的判断依据 |
| version | 工具改签名后旧任务回放会炸 |
| timeoutMs | 慢工具拖死整个任务 |

[ToolRegistry](../src/main/java/com/xb/agent/tool/ToolRegistry.java) 用 ConcurrentHashMap 支持运行时 register/unregister，**不重启服务**就能上下线工具——配合配置中心推送就是生产形态。

## 权限校验的位置

[ToolPermission](../src/main/java/com/xb/agent/tool/ToolPermission.java) 拦在注册中心和执行器之间，**而不是让每个工具自己校验**。散落在各工具里，漏一处就是越权事故。集中校验 + 权限标签，一眼能审出全量规则。

## 执行器：熔断 + 错误分类反馈

[ToolExecutor](../src/main/java/com/xb/agent/tool/ToolExecutor.java) 的两个关键设计：

### 1. 错误分类而不是统一捕获

```java
catch (IllegalArgumentException e) → "[ERROR] 参数错误...建议修改入参后重试"
catch (Exception e)               → "[ERROR] 工具执行失败...如为网络问题可重试，否则建议换方案"
```

网络错误重试、参数错误不重试——而且错误信息**结构化返回给 LLM，让 Agent 自己决策**（重试/改参数/终止），比硬编码错误处理灵活得多。

### 2. Resilience4j 熔断 + 降级反馈

`@CircuitBreaker(name = "toolCircuitBreaker", fallbackMethod = "degraded")`，降级返回 `[DEGRADED] 请改用其他工具或稍后重试`——**降级不是吞错误，是给 Agent 一条可走的路**。

## undo 回滚设计成可选

[AgentTool](../src/main/java/com/xb/agent/tool/AgentTool.java) 的 `undo` 是 default 方法抛 UnsupportedOperationException：只读工具不用写空实现，写操作工具必须实现。回滚的难点不在接口在**语义**——"删除订单"的 undo 是恢复记录还是标状态，业务说了算。

## 示例工具

[DemoTools](../src/main/java/com/xb/agent/tool/DemoTools.java) 三个工具各演示一个横切点：
- orderQuery：LOW 风险只读
- orderDelete：HIGH 风险 + undo 实现
- externalApi：70% 概率超时，演示熔断触发

工具本身逻辑刻意保持简单（学习项目），复杂度都应该在横切层。
