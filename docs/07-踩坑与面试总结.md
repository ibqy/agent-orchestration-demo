# 踩坑与面试 —— 学习总结

> 本项目踩过的坑 + 对应面试高频题的标准答案（自己的话）。

## 踩坑记录

### 1. LangChain4j 1.0.0 的 API 断代
`ChatLanguageModel.generate()` 在 1.0.0 系列被移除，接口改名 `ChatModel`，方法 `chat()`。并行写模块时 reasoning 包用了新 API、multi 包用了旧 API，静态检查才抓出来。教训：**跨模块接口约定要先冻结再并行开发**。

### 2. Statemachine 的状态机 ≠ 持久化状态机
Spring Statemachine 是内存态，重启即丢。任务断点续跑真正依赖的是**快照**，框架的 FSM 只负责流转合法性校验。source of truth 是 Redis 里的快照。

### 3. Redis 同 key 类型冲突
LoopBreaker 第一版对同一个 key 又 `opsForValue().get` 又 `opsForList().rightPush`，第二次调用必抛 WRONGTYPE。**一个 key 一种类型，开工前定死**。

### 4. Reviewer 与 Worker 互相拉扯
Reviewer 判 RETRY → Worker 重跑 → Reviewer 还判 RETRY → 无限循环。所有 Agent 间交互必须有重试上限（本项目 2 次）。

### 5. 工具清单必须注入 prompt
LLM 不知道有什么工具就会编造工具名（幻觉调用）。工具清单拼进任务上下文后，幻觉调用归零。

## 面试高频题速答

### Q1: 单 Agent vs 多 Agent 怎么选？
任务 1-2 步用单 ReAct；子任务可并行拆分、或需要角色制衡（执行+评审分离）才上多 Agent。多 Agent 每层交互都是 LLM 往返，延迟和成本翻倍不是白来的。

### Q2: 断点续跑怎么实现？
快照设计反推法："重启后我要从哪继续" → 计划 JSON + 已完成子任务 ID + 执行轨迹 + token 计数。每次状态流转立即落 Redis，恢复时从快照重建上下文。

### Q3: HITL 怎么做？
高危工具触发 NEED_HUMAN 事件，状态机 RUNNING → WAIT_HUMAN，快照已落盘。人工确认接口发 HUMAN_CONFIRM 恢复。本质是状态暂停 + 快照 + 恢复三件套。

### Q4: 三种记忆什么时候用哪个？
按查询方式分：最近对话（短时，Redis TTL）、语义召回（长时，向量库）、精确查询（实体，结构化）。订单号过向量检索是浪费。

### Q5: Agent 死循环怎么防？
三层：总调用次数上限、重复签名检测（同工具同参数连续 3 次）、token 预算强制终止。让 LLM 换参数比重试有效。

### Q6: 工具注册中心怎么设计？
描述符（名称/参数/权限/风险/版本）+ 运行时动态注册下线 + 权限标签集中校验。发现和执行分离，LLM 只看描述符清单。

### Q7: Plan-and-Solve 和 ReAct 的差异？
ReAct 每步现想，适合未知问题；PnS 开局一次规划，适合步骤固定流程。PnS 的坑是初始规划想当然，必须每步校验 + Re-Plan。生产常用混合：粗规划 + 执行中调整。

## 项目短板（诚实清单）

- LongTermMemory 是内存模拟，未接真 Milvus
- 多 Agent 通信是进程内调用，未走 Kafka 消息总线（长任务跨服务才需要）
- HITL 是状态机层演示，未实现"暂停后阻塞等待+恢复续跑"的完整语义
- Statemachine 的 FSM 与 TaskRunner 流转表存在双份定义，生产应二选一

这些短板就是下一个项目的需求清单。
