# 分层记忆 —— 学习总结

> 结论先行：三种记忆不是三种存储，是**三种查询方式**（最近对话 / 相似检索 / 精确查询）。

## 先纠正一个混淆

以前把 ChatMemory、任务快照、长期记忆混为一谈，实际职责严格分开：

| 概念 | 存的是什么 | 生命周期 | 代码 |
|------|-----------|---------|------|
| 短时记忆 | 本次任务的对话/思考链 | 会话级（2h TTL）| [ShortTermMemory](../src/main/java/com/xb/agent/memory/ShortTermMemory.java) |
| 任务快照 | 任务执行进度 | 任务级（7 天）| TaskSnapshot（state 包）|
| 长时记忆 | 用户长期知识 | 永久 | [LongTermMemory](../src/main/java/com/xb/agent/memory/LongTermMemory.java) |
| 实体记忆 | 订单号/用户名等结构化字段 | 永久 | [EntityMemory](../src/main/java/com/xb/agent/memory/EntityMemory.java) |

## 三层检索顺序

[LayeredMemoryService.buildContext](../src/main/java/com/xb/agent/memory/LayeredMemoryService.java) 的注入顺序：

1. **实体**（精确）→ 订单号这种字段过向量检索是浪费，结构化查询 1ms
2. **长时**（向量）→ 用户偏好、历史工单，语义召回
3. **短时**（最近 N 条）→ 压缩后拼入

## 记忆压缩的提前量

[MemoryCompressor](../src/main/java/com/xb/agent/memory/MemoryCompressor.java) 在 70% 窗口就触发压缩，不是 100%——**压缩本身也要消耗 token 和时间**，等满了再压就来不及了。压缩 prompt 只保留：任务结论、关键数据、遗留问题，删掉过程描述。

## 写入时机选"任务完成时"

[onTaskFinished](../src/main/java/com/xb/agent/memory/LayeredMemoryService.java) 里长时记忆只在任务结束时抽取写入。每轮对话都写的话，库很快被琐碎内容灌满，**召回质量反而下降**——这是记忆和日志的本质区别：记忆要贵精不贵多。

## 遗忘机制

短时记忆交给 Redis TTL 自然过期。学习项目没做长时记忆淘汰，生产应该按"最后被召回时间 + 权重"做 LRU 淘汰，重要记忆定期被召回就续期。

## 学习项目的简化声明

[LongTermMemory](../src/main/java/com/xb/agent/memory/LongTermMemory.java) 用内存 Map + 二元组粗匹配模拟向量检索，生产替换 Milvus EmbeddingStore 一行接口不变（recall 签名已按向量检索设计）。
